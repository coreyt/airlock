# 0.5.9 verification and review record

## TDD evidence

The verification pass added `tests/test_0_5_9_features.py`.  It first exposed
two behavioural defects as RED tests:

1. Adaptive semantic metadata marked a short-circuited heavy classifier as
   selected.  GREEN records only classifiers actually executed.
2. MCP post-tool responses did not carry code-inspection evidence.  GREEN
   persists the same safe category/count result used for normal responses.

Review then found two regressions/security gaps. Tests were added before their
fixes: `--llm` does not write knobs, and the mutation renderer never exposes
raw ledger before/after values. The test suite also protects the replacement
range-to-analysis mapping after removal of the days input.

## Independent review

An independent agent reviewed the uncommitted implementation. Findings fixed
in this pass: broken Run Analysis `#logs-days` lookup, LLM knob write, mutation
value disclosure, MCP inspection propagation, and adaptive selected metadata.

Closeout remains blocked on material unimplemented planned packs: production
classifier metadata/corpus equivalence and full slow-analysis skip
recommendations. These must not be
represented as released or internally closed until implemented and verified.

The read-only `admin:read` provider snapshot and Overview headroom/spend view
were subsequently implemented with unit coverage. It does not audit reads or
change state, and it renders blanks when the admin perimeter is unavailable.
The provider-budget alert now evaluates the same configured caps and rolling
spend, while zero or absent caps remain non-alerting.

The optional remote Anthropic analyzer executor is explicit-only
(`AIRLOCK_ANALYZER_REMOTE_SANDBOX=anthropic`) and locked under the `analyzer`
extra. Tests prove remote payload minimization, opt-in gating, structured-output
validation, and deterministic fallback behavior.

Adaptive selection evidence now includes selected, skipped, and
short-circuited classifier counts in slow analysis plus advisory-only skip
recommendations. `corpus_equivalence_report()` compares `all` versus
`adaptive` verdicts, classifier skip counts, p95 latency, and mismatches; it
does not alter selection or enforcement. A production corpus run remains a
closeout gate.

## Second independent review

A final independent review was requested after the implementation and test
pass. Its correctness findings fixed in RED/GREEN cycles were:

- managed MCP readiness probes now receive the remaining startup deadline as
  their HTTP timeout, so a short configured deadline cannot be overrun by the
  default five-second probe;
- canonical request-event construction merges top-level and nested LiteLLM
  metadata without breaking nested-object identity, preserving normal-response
  code-inspection observations;
- the mutation ledger renders the canonical redaction count; and
- LLM structured output rejects non-string evidence references and non-list or
  non-string proposed actions.

The review also identified unresolved closeout blockers: the normal LLM path
is not yet a real bounded client-side tool loop, the optional Anthropic path is
a minimized remote Messages API executor rather than a provider sandbox
integration, code-inspection weights are not connected to a post-response
enforcement path, and log loading/blocked-client aggregation need the remaining
bounded-query semantics. The internal milestone must not receive its closeout
marker until they are resolved.

## Closeout-finding dispositions — 2026-08-04

The four blockers from the second independent review are resolved as follows.
Design and rationale: [`design-0.5.9-closeout-findings.md`](design-0.5.9-closeout-findings.md).

| # | Finding | Disposition |
|---|---|---|
| F-4 | Log loading / blocked-client aggregation need bounded-query semantics | **Implemented** |
| F-1 | Normal LLM path is not a real bounded client-side tool loop | **Part A implemented; Part B deferred to 0.5.10** |
| F-2 | Anthropic path is a Messages API executor, not sandbox integration | **Re-scoped by owner: claim corrected, code unchanged** |
| F-3 | Code-inspection weights not connected to post-response enforcement | **Out of scope by owner; misleading field removed** |

**F-4.** `airlock/log_query.py` is now the single bounded reader. It filters
while scanning, walks days newest-first, and reports truncation via
`LogPage.truncated`/`limit_hit`, which the analyzer and advisor surface rather
than dropping. `advisor/tools.get_recent_errors` no longer passes
`limit=1000000`, and its failure filter runs during the scan.

**F-1 Part A.** `_run_tool_loop` returns a `ToolLoopOutcome` with an explicit
`stop_reason` and enforces a `ToolLoopBudget` (rounds, wall-clock, total tool
calls, per-result bytes). Previously the only bound was a round count and every
failure returned a bare `None`. Part B — parameterized tool arguments — is
deferred to 0.5.10 because it should be served by the F-4 bounded reader; adding
arguments first would let a model request an arbitrarily large slice.

**F-2.** Behavior unchanged. The over-promise is corrected in
`docs/guide/guardrails.md`: Airlock does not manage, verify, or retrieve results
from a sandbox — it declares the provider's `code_execution` tool on a Messages
API call. The opt-in controls whether derived aggregates leave the machine; it
is not a security boundary. `AIRLOCK_ANALYZER_REMOTE_SANDBOX` keeps its name for
compatibility, now documented for what it is.

**F-3.** Code inspection remains observational; no signal is emitted and the
orchestrator is untouched. The hardcoded `"enforcement_weight": 0.0` was removed
with owner approval: a field of that name in persisted evidence advertised a
wiring that did not exist — the same over-promise category as F-2. Connecting
inspection to enforcement would require its own observe window first, since
`resource_access` matches ordinary code-assistance traffic.

Suite after these changes: **2986 passed, 107 skipped, 1 xpassed**. Ruff clean;
strict MkDocs build clean.

## Observe-window gate — re-scoped 2026-08-04

The second review's closeout blockers are resolved (above). The remaining gate
was the production observe window introduced when the local operational corpus
was declined.

**Owner decision: re-scope it to the local tripwire.** Model Armor is disabled
in production, so an observe window here produces tripwire evidence only. The
semantic tier ships as a benchmark-validated capability this deployment does not
enable; `shadow` and `enforce` are out of scope for it here, and any deployment
that does enable it inherits the original obligation to observe before promoting.

This is a waiver of a gate for a disabled component, not a claim that the
evidence exists. The distinction matters: the benchmarks measure detection
quality, not this deployment's false-positive rate, and nothing in 0.5.9 should
be read as establishing the latter for the semantic tier.

The tripwire's own observe evidence is reviewable with `airlock semantic-report`
and already shows false positives on security-related prose — the quoted-benign
class the benchmarks predicted.

With that, all closeout preconditions are met and
`milestone/0.5.9-internal-closeout` was created on the final CI-green commit.
