# 0.5.8 enforcement design — measurement before rejection

**Status:** independent local design/source/test review passed on 2026-08-02; see
[`0.5.8-enforcement-design-independent-review-2026-08-02.md`](../plans/runs/0.5.8-enforcement-design-independent-review-2026-08-02.md).
This document defines the intended contracts and gates for P-2 reasoning-effort
validation and P-2b cross-tier fuzzy resolution. It does not authorize either
enforcement behavior before its evidence is complete.

## 1. Scope and non-goals

P-2 replaces silent `reasoning_effort` translation with a model-aware 400 when the
requested value is known invalid. P-2b refuses fuzzy resolution only when a pre-existing
near match would cross a configured cost tier. Both convert previously successful
requests into errors, so both require measured evidence.

This design does not change Airlock's client authorization model, add per-client model
entitlements, modify model pricing, or perform a live provider call. Existing
dropped-qualifier refusal stays as-is.

## 2. Current behavior and evidence boundary

`airlock.reasoning_effort.normalize_reasoning_effort()` still translates off-intent
values before LiteLLM `drop_params`: OpenAI/Azure to `minimal`, Gemini to `disable`,
and Anthropic by dropping the parameter. For OpenAI-family calls it also evaluates the
original client value against LiteLLM capability flags and emits WARNING
`effort_would_reject` plus a mutation-ledger `inject` record. The effort window runs
2026-07-21 through 2026-08-21; queryability, affected-client reporting, and a
per-caller disposition remain required.

`ModelAliasTable.resolve()` still refuses a match only if it would discard a
non-numeric qualifier. That guard is already enforcing and intentionally has no
pre-existing-traffic evidence. The committed P-2b measurement seam uses
`_TIER_AMBIGUITY_MARGIN` to retain a cross-tier diagnostic from the same fuzzy scoring
pass and the guardian emits `fuzzy_match_would_reject` plus a ledger marker without
changing the selected alias. It is not yet deployed. Therefore the active effort
window is not evidence for P-2b; deploy the dedicated measurement pack, verify it is
queryable, then observe a full billing cycle.

The ledger is carried into the normal callback event builder, but queryability in the
deployed event sink is still a gate to verify, not an assumption. The event report must
distinguish a real zero from a callback/sink path that has not been exercised.

## 3. Shared gates and review gates

No enforcing implementation may be written or merged until its design review passes.
No enforcing implementation may be released until all applicable gates close:

| Gate | P-2 | P-2b |
|---|---:|---:|
| Independent design review records PASS | required | required |
| Stable warn-only event reaches RequestEvent/ledger and is queryable | required | required |
| Full billing-cycle observation | 2026-07-21 → 2026-08-21 | starts only after P-2b instrumentation deploys |
| Affected-client report and per-caller notify/grace/enforce decision | required | required |
| Funded live verification of OpenAI `reasoning_effort=max` | required | not applicable |
| Implementation review with focused behavior and regression tests | required | required |

The live `max` call is intentionally not performed by this work: it spends provider
funds and needs a funded key/operator approval. If the call cannot be made, P-2 stays
blocked; a missing LiteLLM flag is not a basis for rejection.

## 4. P-2 enforcing contract

1. Resolve the requested Airlock alias through `model_list` to its LiteLLM body before
   calling `litellm.get_model_info`; try the full provider body and bare body.
2. Derive supported levels from LiteLLM per-level capability flags. An unknown or
   unresolvable model passes through unchanged: custom and self-hosted models must not
   be rejected from ignorance.
3. A known supported value passes untouched. There is no normalization and no
   success-path mutation ledger record.
4. A known unsupported value returns HTTP 400, OpenAI-shaped:

   ```json
   {"error":{"type":"invalid_request_error","code":"invalid_reasoning_effort","param":"reasoning_effort","message":"reasoning_effort 'none' is not supported by 'openai/gpt-5.4'; use one of: high, low, medium, minimal.","airlock":{"requested":"none","model":"openai/gpt-5.4","supported":["high","low","medium","minimal"]}}}
   ```

5. `max` has no assumed result. The funded live result must be recorded with the
   model and provider response before it changes the capability decision.
6. The configuration name becomes `AIRLOCK_VALIDATE_REASONING_EFFORT`, default `1`.
   Setting it to `0` is the explicit operational escape hatch that restores LiteLLM
   `drop_params` behavior. `AIRLOCK_NORMALIZE_REASONING_EFFORT` is accepted only as a
   deprecated fallback while the new variable is unset, emits a deprecation warning,
   and is removed in the next breaking release. This is not a permanent warn-only
   branch: it only controls validation after the enforcement release.

Tests must cover semantic alias body resolution, unknown-model pass-through, valid
pass-through/no ledger mutation, invalid 400 shape, `max` outcome, Gemini and
Anthropic behavior, and the explicit escape hatch. Tests mock LiteLLM capability data;
they must not depend on the mutable live model map.

## 5. P-2b enforcing contract

Exact aliases always resolve. A fuzzy match within the same configured cost tier may
continue to resolve. A fuzzy match whose best valid candidate crosses a configured
cost tier returns the existing OpenAI-shaped `AirlockModelNotFound` 404 with
`X-Airlock-Model-Suggestion`; it does not introduce a second header grammar. The body
continues to use `error.code=model_not_found`, `error.param=model`, and ranked
`error.airlock.suggestions`.

### 5.1 Exact classifier (shared by measurement and enforcement)

Do not implement the decision by re-scoring in the guardian or by parsing a log line.
`ModelAliasTable` must return one structured resolution detail from the same scoring
pass that selects the current alias. Exact and provider/body matches have no fuzzy
diagnostic. For a fuzzy result at or above `_WARN_THRESHOLD`, collect every distinct
alias whose score is at least `max(_WARN_THRESHOLD, best_score -
_TIER_AMBIGUITY_MARGIN)`. Look up their configured tiers.

- If every candidate has one identical, non-empty tier, it is same-tier and may route.
- If two or more configured tiers are present, it is cross-tier ambiguous. In
  measurement, preserve the current best-alias route; after the gate, return 404.
- If a candidate lacks a tier, fail open for this feature and log a configuration
  diagnostic. An unclassified alias must not become a rejection merely because the
  tier table drifted.

For a cross-tier event, `served` is the current best alias, `suggested` is the
highest-scored alternate-tier alias, `from_tier` is the current best alias's tier, and
`to_tier` is the alternate's tier. Stable tie-breaking must use the existing alias
order so the measurement output and later 404 suggestions do not fluctuate. The
measurement/enforcing test matrix must include ties, aliases without a tier, and a
cached repeated request.

The measurement pack must preserve today's chosen alias and emit one WARNING event:

```
event=fuzzy_match_would_reject requested=<input> served=<current alias>
suggested=<candidate> score=<score> from_tier=<tier> to_tier=<tier> client_id=<id>
```

It must also append a content-safe ledger marker. Verify it reaches the deployed
RequestEvent sink before using it for a report; logs alone are insufficient. Its routing
result must be byte-identical to the pre-instrumentation result across exact, same-tier
fuzzy, cross-tier fuzzy, and unmatched cases.

Airlock currently has a global configured catalog, not per-client catalog filtering.
The current suggestion contract is consequently limited to that global catalog. If
per-client model authorization is later introduced, suggestion ranking must receive an
allowed-alias set before selecting or exposing candidates; P-2b must not claim an
entitlement guarantee that the current system cannot enforce.

Tests must cover same-tier resolution, cross-tier warn-only evidence, post-gate 404,
current 404/header grammar, no-cache behavior for rejected inputs, event field
completeness, RequestEvent queryability, and any future entitlement filter.

## 6. Rollout and rollback

For P-2: finish the active report on 2026-08-21, record affected callers and
dispositions, make the funded `max` call, review the enforcing patch, then enable the
default validation behavior in a release. The named validation escape hatch is the
short-term operational rollback; using it must be logged and followed by a client
remediation ticket.

For P-2b: build and review measurement first, observe a full cycle, publish an
independent report and disposition, then follow the same reviewed enforcement flow.
There is no date-based shortcut: absence of instrumentation is a blocker, not a zero
result.

## 7. Acceptance evidence

The enforcing pull request must include focused unit/integration tests, lint/type
checks, the relevant normal test suite, a review artifact with a PASS verdict, the
measurement report, the caller disposition record, and release notes that describe the
new 400/404 behavior. The 0.5.8 plan and release board are updated only from those
witnesses.
