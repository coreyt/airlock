# 0.5.8 enforcement design — independent local review protocol

**Status:** READY FOR REVIEW. This is a local, evidence-backed review gate; it does
not require sending repository material to an external service.

## Independence rule

The reviewer must be a separate human or separately tasked agent who did not author
the design or the corresponding implementation patch. The reviewer has read-only
scope. A separate agent in this repository session satisfies that rule when its task
is explicitly an adversarial review and its findings are preserved verbatim in the
result artifact.

## Adversarial checklist

Record an anchor and pass/fail result for every item.

| # | Review question | Required evidence |
|---|---|---|
| R1 | Does P-2 reject only known-invalid OpenAI-family values and fail open for unknown/custom models? | Alias-to-body resolution and mocked capability-map tests. |
| R2 | Is client intent—not a normalized outbound value—what the P-2 measurement and later 400 evaluate? | `normalize_reasoning_effort()` ordering plus warning/ledger tests. |
| R3 | Is `max` unresolved without provider evidence, with no capability result inferred from a missing LiteLLM flag? | `openai-reasoning-effort-max-probe.md` and its contract test. |
| R4 | Can the P-2 error be made OpenAI-shaped, stable, and operably reversible? | Design §4, `proxy_errors.py`, required enforcing-test matrix. |
| R5 | Does P-2b use one scoring pass, stable ordering, and preserve present routing during measurement? | `resolve_with_diagnostic()` and model-alias tests. |
| R6 | Does P-2b reject only a configured cross-tier ambiguity and fail open if tier data are missing? | Tier-diagnostic branches and tests for missing tiers/ties/cache. |
| R7 | Are `effort_would_reject` and `fuzzy_match_would_reject` independently observable through the mutation ledger and RequestEvent, not only logs? | Guardian/reasoning code plus request-event tests. |
| R8 | Does each enforcement path wait for its own deployed, queryable full-cycle report and per-caller disposition? | Both measurement-window runbooks; no date shortcut. |
| R9 | Do existing 404/header contracts and dropped-qualifier enforcement stay unchanged? | `proxy_errors.py`, suggestion tests, and response-header docs. |
| R10 | Are rollback, documentation, and focused implementation/review test obligations explicit before behavior can change? | Design §§6–7 and release checklist. |

## Verdict rule

- **PASS:** all ten items pass; any low-risk concern has a named test/doc follow-up
  that does not change the enforcement contract.
- **CONCERNS:** no unsafe contract flaw, but one or more follow-ups must be resolved
  before implementation review.
- **BLOCK:** any ambiguous rejection condition, missing fail-open path, missing
  observability route, or an attempt to treat missing provider evidence as support.

The reviewer records their result in
`dev/plans/runs/0.5.8-enforcement-design-independent-review-YYYY-MM-DD.md`, including
their identity/persona, exact inputs, anchored findings, verdict, and commands/tests
checked. A PASS permits an enforcing patch to be designed and reviewed; it does not
override the separate measurement-window or provider-probe evidence gates.
