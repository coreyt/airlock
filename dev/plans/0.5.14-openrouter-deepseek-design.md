# Airlock 0.5.14 — OpenRouter and DeepSeek integration design

## Status and decision

This is a design for the 0.5.14 implementation. It is intentionally limited to
Airlock integration, documentation, and verification. The exact locked
dependency is LiteLLM 1.94.1, which already has native adapters and model
registries for both `openrouter` and `deepseek`. Airlock must not implement a
second provider adapter, a second OpenAI-compatible transport, or a copy of
LiteLLM's model registry.

The deployment has runtime-only `OPENROUTER_API_KEY` and `DEEPSEEK_API_KEY`
secrets in `.env`. They are not read, copied, logged, added to tracked YAML, or
used by unit tests. They may be used only for the explicitly documented funded
smoke tests after the code and no-credit tests pass.

## Requirements

### Common requirements

- **R1 — Explicit configuration.** An operator exposes a provider only by
  adding reviewed `model_list` entries. Each entry uses a stable Airlock alias,
  LiteLLM's canonical provider/model body, and an `os.environ/...` secret
  reference. Neither provider is silently enabled by the presence of an
  environment variable.
- **R2 — Provider secrets and error metadata stay out of artifacts.** Keys,
  authorization headers, OpenRouter routing metadata, and provider-supplied
  `user_id` values must not be rendered in config examples, discovery output,
  response headers, TUI snapshots, test fixtures, JSONL error fields, or
  application error logs. `.env` remains ignored. This provider slice does not
  change Airlock's existing, separately governed request/response-content
  logging policy; its documentation must state that boundary honestly.
- **R3 — Airlock controls remain invariant.** Requests still traverse the
  existing authentication, guardrails, alias resolution, routing, circuit
  breaker, recorder, and response-transparency paths. Provider discovery is
  informational only: it never authorizes a model, changes a configured alias,
  or changes routing.
- **R4 — Exact aliases, no silent substitution.** An OpenRouter or DeepSeek
  request must resolve only to a configured Airlock alias. A provider-prefixed
  canonical name may resolve through the existing exact alias table only when
  its configured body is identical. Fuzzy matching must retain the existing
  cost-tier and qualifier protections.
- **R5 — Failure boundary.** Airlock must retain the ordinary LiteLLM exception
  classification at its callback boundary. Authentication and balance failures
  are not retried as availability failures; rate-limit and transient provider
  failures remain observable by the existing provider-protection/circuit-breaker
  paths. A provider's `Retry-After`, where LiteLLM exposes it, remains on the
  LiteLLM exception response; current Airlock rate-limit observation neither
  persists it nor promises to propagate it to the client. It must not be turned
  into an Airlock policy error.
- **R6 — Honest attribution.** `X-Airlock-Served-By` reports the LiteLLM served
  provider token, not a guess based on the requested alias. It is `deepseek`
  for DeepSeek and `openrouter` for OpenRouter. For OpenRouter it must *not*
  claim to identify the upstream model host selected by OpenRouter; that routing
  is outside Airlock's control.
- **R7 — No default cross-provider fallback.** This work adds no implicit
  fallbacks, retries, cost tiers, budgets, or model entries. An operator may
  configure them using the existing reviewed Airlock settings. Any OpenRouter
  fallback/routing policy is chosen at OpenRouter and documented as such.

### OpenRouter requirements

- **OR1 — Canonical configuration.** The documented model body format is
  `openrouter/<publisher>/<model>`, for example
  `openrouter/openai/gpt-4o-mini`, with
  `api_key: os.environ/OPENROUTER_API_KEY` and explicit
  `api_base: https://openrouter.ai/api/v1`. An alternate `api_base` is an
  operator override, not a different Airlock transport.
- **OR2 — Optional catalog discovery.** When startup discovery is enabled and
  at least one configured OpenRouter entry resolves a key, Airlock queries
  the `models` URL derived from that entry's reviewed `api_base`, with bearer
  authentication. Entries for a provider must use the same base URL for one
  discovery pass; otherwise discovery skips that provider. Every returned `id`
  is presented as `openrouter/<id>`; nested publisher/model IDs remain intact.
  Discovery failures log only provider name, exception class, and (for HTTP
  failures) status code; they never block startup.
- **OR3 — Routing/privacy boundary.** Documentation identifies OpenRouter as a
  gateway. Airlock can report `openrouter` as the immediate served provider but
  does not expose optional OpenRouter app/site metadata or upstream fallback,
  provider, retention, or data-policy decisions by default.

### DeepSeek requirements

- **DS1 — Canonical configuration.** The documented model body format is
  `deepseek/<model>`, for example `deepseek/deepseek-chat`, with
  `api_key: os.environ/DEEPSEEK_API_KEY` and explicit
  `api_base: https://api.deepseek.com`. LiteLLM 1.94.1 otherwise defaults its
  DeepSeek transport to `/beta`; setting the stable base explicitly is required
  for this release. An operator must explicitly opt into a provider beta
  endpoint or model.
- **DS2 — Optional catalog discovery.** When startup discovery is enabled and
  at least one configured DeepSeek entry resolves a key, Airlock queries
  the `models` URL derived from that entry's reviewed `api_base`, with bearer
  authentication. Entries for a provider must use the same base URL for one
  discovery pass; otherwise discovery skips that provider. Every returned `id`
  is presented as `deepseek/<id>`. A failure is best-effort, sanitized, and
  does not block startup.
- **DS3 — Request privacy.** Airlock does not map `X-Airlock-Client` or an
  authenticated client identity into DeepSeek's optional `user_id`. A future
  mapping requires a separate privacy decision, an operator-controlled switch,
  and a non-identifying value.
- **DS4 — Narrow tool contract.** DeepSeek support covers OpenAI function
  tools only. Airlock must reject a non-function tool with an OpenAI-shaped 400
  before LiteLLM dispatch, rather than allow LiteLLM 1.94.1 to drop it. JSON
  mode is not a 0.5.14 compatibility claim unless a separately pinned
  provider/model contract and regression prove it.

## Architecture review

| Existing seam | Finding | Design consequence |
|---|---|---|
| LiteLLM `model_list` dispatch | LiteLLM 1.94.1 already owns both adapters and their request/stream parsing. | Add no dispatch adapter or request parser. Document canonical model bodies and use ordinary `litellm_params`. |
| `airlock/models_catalog.py` | Built-in discovery covers OpenAI, Anthropic, Mistral, Gemini, and Perplexity only. Its generic OpenAI-compatible fetcher already preserves slash-containing IDs and resolves an `os.environ/...` key from `model_list`, but fixed fetchers ignore a model entry's `api_base` and log `str(exc)` verbatim. | Add two thin built-in fetchers through `_fetch_openai_compatible`; derive a consistent provider's discovery URL from its reviewed `api_base`, and replace discovery exception text with an allowlisted class/status record. |
| `fast.router.set_router_config` and `capability.airlock_provider_for` | Provider identity comes from the prefix in the configured `litellm_params.model`, not a provider-specific hard-coded registry. Circuit-breaker fallback filtering is similarly alias-catalog based. | No general router, alias-table, circuit-breaker, budget, or capability-code change is required for configured `openrouter/...` or `deepseek/...` entries. Add one narrow DeepSeek non-function-tool validation after final alias/routing resolution in `AirlockFastGuardian.async_pre_call_hook`, before dispatch/circuit-breaker work. |
| `transparency.attribute_served_backend` | It reads LiteLLM's actual served provider correctly, but its classification sets only recognize existing providers. Both new tokens would currently be `unknown`. | Classify `deepseek` as `native` and `openrouter` as `gateway`; extend attribution and documentation tests. The exposed provider token remains `openrouter`, never a guessed downstream host. |
| `fast.monitor` | Existing callbacks record attempts/failures by configured provider and record rate-limit headers from a LiteLLM exception response. | Add characterization tests for representative LiteLLM-shaped 401/402/429/500/503 outcomes. Do not add a provider-specific retry loop; change handling only if a test proves the existing boundary loses a supported signal. |
| Request-event, monitor, tracing, and enterprise projections | The generic request logger records normal request/response content under its existing policy. More critically, LiteLLM's OpenRouter stream exceptions can embed `metadata` and `user_id`, and Airlock currently serializes/logs exception text; monitor also persists it as a provider-protection reason and optional tracing exports it. | Add one shared provider-error sanitizer used by request-event projection, monitor/provider-protection metadata and logs, tracing, and enterprise projection. It emits a bounded provider/status/error-type record and no free-form provider exception text; typed HTTP status/exception inspection happens before replacement so 429 handling is retained. |
| DeepSeek request transformation | LiteLLM 1.94.1 drops non-function DeepSeek tools before dispatch. | Add a narrow DeepSeek pre-dispatch validation rule that returns an OpenAI-shaped 400 for non-function tools. Do not claim generic tool types or JSON mode. |
| Config/templates and docs | The repository documents explicit aliases and keeps `.env` ignored, but currently offers no examples for these providers. | Add docs-only examples with explicit stable `api_base` values; do not add an enabled provider/model to the shipped default configuration, which would expand a deployment's public model surface merely because a key exists. |

## Design

### 1. Operator configuration

The implementation adds a configuration-guide section with examples like these.
They are examples, not default entries in `config.yaml` or its template.

```yaml
model_list:
  - model_name: openrouter/openai/gpt-4o-mini
    litellm_params:
      model: openrouter/openai/gpt-4o-mini
      api_key: os.environ/OPENROUTER_API_KEY
      api_base: https://openrouter.ai/api/v1

  - model_name: deepseek/deepseek-chat
    litellm_params:
      model: deepseek/deepseek-chat
      api_key: os.environ/DEEPSEEK_API_KEY
      api_base: https://api.deepseek.com
```

An operator may create a separate short alias, but the provider-prefixed alias
is the stable contract. The guide explains that model availability, OpenRouter
upstream routing, cost, and data retention are provider controls; Airlock
enforces only the controls at its own boundary.

### 2. Informational model discovery

Add `_fetch_openrouter_models` and `_fetch_deepseek_models` as small wrappers
over the existing `_fetch_openai_compatible` helper. Register them in
`_FETCHERS` with prefixes `openrouter` and `deepseek`. Their base URL comes from
the configured provider entries, not a separate fixed default. Before sending a
key, discovery requires exactly one normalized HTTPS base URL for that provider
and derives its `models` endpoint from it. The base must have a hostname, no URL
credentials, query, or fragment, and a path ending in either the API root or
`/chat/completions`; the latter is stripped before `/models` is appended. A
`/models` input is rejected. An absent, malformed, or conflicting base skips
discovery with a sanitized warning. The request uses a no-redirect opener, so a
cross-origin redirect cannot receive the key. Consequently a key configured for
a private endpoint is never sent to the public default or a redirect target.

The generic helper's `f"{provider_prefix}/{model_id}"` result is deliberately
used. It preserves OpenRouter IDs such as `openai/gpt-4o-mini` as
`openrouter/openai/gpt-4o-mini`, and DeepSeek IDs as
`deepseek/deepseek-chat`. The existing concurrency, bounded timeout, and
best-effort failure posture apply unchanged. Replace the current verbatim
`str(exc)` discovery warning with provider name, exception class, and HTTP
status when present—never exception text, URL query, or headers. No discovery
result is written back to YAML, added to LiteLLM's router, or treated as a
permission grant.

### 3. Attribution and observability

Extend `airlock.transparency` provider classes:

- `deepseek` is a native provider.
- `openrouter` is a gateway provider.

The existing served-attribution read remains the sole source for response
headers, request events, JSONL, and TUI displays. The work does not introduce
OpenRouter-specific headers or surface opaque vendor headers. This avoids an
incorrect claim that Airlock knows which OpenRouter upstream served a request.

### 4. Failure and streaming boundary

LiteLLM remains the only provider transport and streaming parser. Airlock adds
a shared provider-error sanitizer before raw exceptions enter `RequestEvent`,
monitor/provider-protection state and logs, tracing, or an enterprise JSONL
error field. It records only a bounded error type, provider token, and HTTP
status where available; typed status inspection occurs before replacement so
429 detection is unchanged. It does not preserve arbitrary provider exception
text. Airlock's implementation then adds regression/characterization tests at
the callback boundary for:

- standard and streaming success attribution;
- `401` and `402` as non-retryable provider/account conditions;
- `429` and `500`/`503` as provider availability outcomes; an upstream
  `Retry-After` remains available only on the LiteLLM exception response and is
  not an Airlock persistence or client-header contract;
- redaction of distinctive upstream `metadata`, `user_id`, and credential-like
  values from provider failure events and application/JSONL error logs.

DeepSeek function tools are sent normally. Any non-function tool is rejected
before dispatch with an OpenAI-shaped 400, which is safer and more transparent
than LiteLLM's current drop behavior. If an actual LiteLLM 1.94.1 DeepSeek
stream fails its documented keep-alive behavior, the failure must be reduced to
a focused test first. Only then may Airlock add a minimal boundary adaptation;
it must not fork general SSE parsing.

### 5. Documentation and funded smoke

The configuration guide, routing guide, provider-observability guide, and
operations environment-variable table will describe the two keys, exact model
forms, discovery behavior, attribution semantics, and the no-default-enable
posture. The funded smoke procedure uses a minimal non-sensitive prompt through
the Airlock proxy for one configured model per provider, once non-credit tests
are green. It records only timestamp, provider alias, HTTP outcome, stream
completion outcome, and safe Airlock response headers; never a key, prompt,
completion, or raw upstream headers.

## Acceptance criteria

### Configuration and policy

- **AC1.** Documentation contains valid OpenRouter and DeepSeek configuration
  examples using `os.environ/OPENROUTER_API_KEY` and
  `os.environ/DEEPSEEK_API_KEY`; tracked YAML contains no secret values.
- **AC2.** A key in `.env` alone does not expose either provider. An operator
  must add a `model_list` entry and restart.
- **AC3.** A configured provider-prefixed alias produces the correct
  `airlock_provider` record and existing alias/fallback protection cannot route
  it to an unconfigured or different-body model.

### Discovery

- **AC4.** Mocked OpenRouter discovery of `openai/gpt-4o-mini` returns exactly
  `openrouter/openai/gpt-4o-mini`; mocked DeepSeek discovery of `deepseek-chat`
  returns exactly `deepseek/deepseek-chat`.
- **AC5.** Discovery makes no request if the provider has no configured,
  resolvable key, or has an absent, malformed, credential-bearing,
  query/fragment-bearing, or conflicting configured base. It deterministically
  derives `models` from an API root or `/chat/completions` base, rejects a
  `/models` base, and follows no redirect; a cross-origin redirect test proves
  its key never reaches another host. For either provider, an HTTP/network
  failure returns the other successful discoveries and does not prevent startup.
- **AC6.** Discovery output never becomes a model-list entry, routing target,
  authorization decision, or logged credential. A discovery exception carrying
  a sentinel secret produces only provider, exception class, and safe status in
  application logs.

### Attribution, failures, and privacy

- **AC7.** LiteLLM-shaped responses yield `X-Airlock-Served-By: deepseek` with
  `backend_kind: native`, and `X-Airlock-Served-By: openrouter` with
  `backend_kind: gateway`; existing provider classifications remain unchanged.
- **AC8.** Characterization tests cover 401, 402, 429, 500, and 503 at the
  Airlock callback boundary and prove no policy denial is retried or re-labelled
  as an upstream failure. A LiteLLM-exposed `Retry-After` remains only on the
  exception response; its persistence and client-header propagation are out of
  scope.
- **AC9.** A distinctive OpenRouter stream-error `metadata`, `user_id`, and
  credential-like value is absent from `RequestEvent` error fields, JSONL,
  monitor/provider-protection state and logs, and tracing; the bounded error
  category/status remains useful and 429 classification still works. The
  provider slice does not change the separately governed general
  request/response-content logging policy.
- **AC10.** DeepSeek function tools pass through the normal policy path; a
  non-function tool is rejected pre-dispatch with a documented OpenAI-shaped
  400. JSON mode is not advertised unless separately proven for the configured
  model and exact LiteLLM version.
- **AC11.** Documentation states that OpenRouter's downstream-provider choice,
  fallback, pricing, and retention policy are not controlled or verified by
  Airlock.

### End-to-end evidence

- **AC12.** Unit and integration tests for the changed seams pass without live
  credentials or paid calls.
- **AC13.** After AC1–AC12 are green, four manually authorized funded smoke
  calls prove one normal and one streaming completion for each configured
  provider alias. Artifacts retain only the safe fields defined above. A
  provider account/balance failure is recorded as a blocker, not treated as a
  successful integration.

## Out of scope

- Adding a LiteLLM dependency upgrade, custom provider adapter, duplicate
  model/cost registry, or generic OpenAI-compatible proxy layer.
- Auto-enabling a model because an environment variable or discovery result
  exists.
- Default model selection, cross-provider fallbacks, provider budgets, or cost
  tier changes.
- Guaranteeing OpenRouter's downstream provider, privacy, retention, pricing,
  or fallback behavior.
- Sending `X-Airlock-Client`, a virtual-key identity, or customer data as
  DeepSeek `user_id`.

## Implementation order

1. Add and test the two catalog fetcher wrappers, explicit-base guard, and their
   no-key/failure cases.
2. Add and test served-backend classifications.
3. Add the shared error sanitizer, DeepSeek non-function-tool pre-dispatch
   validation, and callback-boundary/error characterization tests.
4. Add configuration and operator documentation, including the funded smoke
   runbook and artifact redaction rules.
5. Run no-credit tests, then perform the manually authorized four-call smoke
   using the existing runtime-only keys.
