# Airlock 0.5.11 — Plan

**Theme: FathomDB as a capability, not a sink.**

FathomDB has been in Airlock as a write-only destination: an optional second
place request records land, behind `AIRLOCK_ENABLE_FATHOM_LOGGER`, off in
production, read by almost nothing. Meanwhile the engine grew the capabilities
Airlock has open issues for — hybrid lexical+vector search (#11), provenance-keyed
erasure, engine-owned projections, bounded graph expansion.

0.5.11 moves to **FathomDB 0.8.21** and uses it for what it can do, rather than
keeping it as a duplicate log sink.

**Status: CLOSED OUT 2026-08-07 — internal milestone, not published.** All
packs landed on branch `0.5.11`: A-1 `31bc1c4`, A-2 `d946090`, A-3 `644f657`,
B-1 `8a6bab8`, B-2 `bde5d44`, C-1+C-2 `0cdefdd`. Suite grew 3107 → 3161
passed, green at every pack boundary in the isolated env
(`UV_PROJECT_ENVIRONMENT=~/.cache/airlock-venvs/0.5.11`); the live proxy and
its venv were never touched.

**Publication (owner decision, 2026-08-07): internal milestone.** Merged to
main and marked with `milestone/0.5.11-internal-closeout`; **no `v*` tag**
(release.yml publishes on any `v*` push) and no version bump — the 0.5.9
pattern. The work ships publicly with the next published release.

**C-2 decisions (owner, 2026-08-07):** analyzer remote default →

## Scope decisions already made

Recorded up front because they remove work the plan would otherwise have to carry:

| Decision | Consequence |
|---|---|
| **No data migration.** 0.8.21 applies to new DB files only | No dual-read, no backfill, no compatibility shim, no migration tests |
| **0.3.1 files are abandoned** | No archive tooling and no read-only legacy path. Old files are orphaned in place |
| **`source_id` = authenticated client ID** | Per-client erasure is the erasure axis. Not per-day, not per-import |
| **Erasure surface: CLI + admin API** | Behind the existing admin perimeter, audited, scriptable |
| **F-3 stays observational across 0.5.x** | Not a deliverable here. Keep collecting; report counts at closeout |

The abandonment is cheaper than it sounds. Only three consumers read the
datastore — Overview billing metrics (`tui/screens/overview.py:213`), the
advisor's `get_recent_errors` (`advisor/tools.py:150`), and the writer itself.
Every other advisor and analyzer path already reads JSONL, and **JSONL keeps full
history untouched**. Abandoning the DB loses a cache, not the record.

## Verified against the real API, not the prose

0.8.21 was installed in a throwaway venv and introspected before this plan was
finalized. Three findings changed the design; they are folded into the packs
below and recorded here so the reasoning is not lost.

**1. Abandoning 0.3.1 files is not inert — it is hazardous.** 0.8.21 opens a
database created by 0.3.1 **without any error**, reports `CounterSnapshot(...
writes=0 ...)` as though it were empty, and then **writes into it successfully**,
producing a file carrying both schemas. Verified end to end. Since the current
default path is `logs/airlock.db` (`datastore.get_db_path`), a 0.8.x build
pointed at an existing state directory would silently adopt the legacy file. A-1
must guard this; "abandoned" cannot mean "ignored".

**2. Degraded retrieval is detectable directly.** `Engine.dense_disabled()` and
`dense_disabled_reason()` are first-class, and `search_text_only()` exists as an
explicit lexical method. B-1 does not have to infer degradation from
`soft_fallback` after the fact — it can ask before searching and pick the honest
method. Better than what this plan originally specified.

**3. Erasure returns a receipt and can fail partway.** `erase_source` returns an
`EraseReport` (not `None`), and `fathomdb.errors.ErasureIncompleteError` exists.
An erasure obligation can therefore half-complete, which B-2 must never report as
done.

Reference signatures confirmed by introspection:

```
Engine.open(path, *, config=None, use_default_embedder=False, **engine_config)
Engine.write(batch: list | None = None) -> WriteReceipt
Engine.erase_source(source_id: str) -> EraseReport
Engine.purge(logical_id: str) -> None
Engine.configure_projections(specs: list[ProjectionSpec],
                             drop: list[str] | None = None) -> ProjectionDelta
Engine.search(query, filter=None, *, rerank_depth=0, use_graph_arm=False,
              alpha=None, pool_n=None, explain=False, view=None) -> SearchResult
Engine.search_text_only(query, view=None) -> SearchResult
ProjectionSpec(name, roles: frozenset[str], fts=False, fts_tokenizer=None,
               vector=False, vector_embedder=None,
               vector_dense_readiness=None, source=None)
ProjectionRole = {FILTERABLE, RANKABLE, SEARCHABLE}
ReadView(include_superseded=False, include_inactive=False,
         include_out_of_window=False, valid_as_of=None)
read.list(engine, kind, predicates=None, *, limit=100, filter=None, view=None)
read.collection(engine, collection, *, after_id=None, limit)   # limit required
```

Capabilities present but **out of scope** for 0.5.11, noted so they are not
rediscovered as surprises: `ingest_with_extractor`, `consolidate_with_provider`,
`record_feedback`, `graph.neighbors` / `graph.search_expand`, `enable_telemetry`
/ `set_profiling` / `set_slow_threshold_ms`, and the `fathomdb.admin` submodule.

## Working environment: how to isolate without breaking production

The live proxy runs `uv run airlock start` with
`WorkingDirectory=~/projects/airlock`, so it uses **this directory's `.venv`** —
and `uv run` auto-syncs. A `fathomdb` pin bump in the main checkout would rewrite
the running service's environment on the next `uv run`.

**A symlinked `.venv` is not sufficient — measured, not assumed.** With
`worktree/.venv -> ~/projects/airlock/.venv`, `uv run` reports
`sys.prefix = <worktree>/.venv` but `realpath` resolves to
`/home/coreyt/projects/airlock/.venv`. The symlink shares the production
environment rather than isolating it, so a dependency change writes straight into
it. That is the exact failure mode the worktree exists to prevent.

**Use `UV_PROJECT_ENVIRONMENT` instead** — uv's supported redirection, verified
working: it created and used an isolated environment, leaving the live venv
untouched (confirmed 1.5G and importing afterwards).

### The working recipe, executed end to end

`uv sync` alone does **not** produce a runnable test environment. Verified by
running the full suite in a fresh isolated venv: **9 failed, 78 errors**, every
one of them PII, because `en_core_web_lg` is not a declared dependency — it is
installed out of band (see `docs/operations.md`) and so `uv sync` never fetches
it. Adding it turned the same suite green at **3107 passed**, matching the live
environment exactly.

```bash
git worktree add .claude/worktrees/0.5.11 -b 0.5.11
cd .claude/worktrees/0.5.11

# Durable location — NOT the repo, and not a session-scoped temp dir
export UV_PROJECT_ENVIRONMENT="$HOME/.cache/airlock-venvs/0.5.11"

uv sync --python 3.12 --all-extras          # pin 3.12; a fresh env defaults to 3.11
uv pip install --python "$UV_PROJECT_ENVIRONMENT/bin/python" \
  "https://github.com/explosion/spacy-models/releases/download/en_core_web_lg-3.8.0/en_core_web_lg-3.8.0-py3-none-any.whl"

UV_PROJECT_ENVIRONMENT="$HOME/.cache/airlock-venvs/0.5.11" uv run --no-sync pytest -m "not live" -q
```

Notes worth keeping:

- **Export `UV_PROJECT_ENVIRONMENT` for every command in the worktree**, including
  `pytest`. Forgetting it on a single `uv run` is what would sync the live venv.
- **Pin the interpreter.** A fresh redirected environment defaulted to CPython
  3.11.15; the project runs 3.12.
- **Sizes:** isolated env 912M before the spaCy model, ~1.3G after; the live venv
  is 1.5G. Disk is not a constraint here (409G free).
- **The symlink shortcut is still fine for packs that change no dependencies**
  (C-1 is pure TUI work) — it avoids rebuilding the environment entirely. Use it
  there and only there; never for A-1.

**Proof of isolation:** after a full sync, a full suite run, and a package
install in the redirected environment, the live venv was unchanged — still 1.5G,
still `fathomdb 0.3.1`, spaCy model intact — and the proxy stayed `active`.

## A-1 — Engine migration to 0.8.21

0.8.x is a different engine: a PyO3 binding to a Rust core, not the 0.3.1 Python
implementation. The pin comment already says so —
`db = ["fathomdb>=0.3.1,<0.4"]  # FathomDB 0.8 requires a storage API migration.`

- Bump to `fathomdb>=0.8.21,<0.9`.
- Rewrite `airlock/datastore.py` against the new lifecycle: `Engine.open(path)`,
  `engine.close`, `engine.drain`, `engine.counters()`.
- **Delete `_ensure_vector_stub_table`.** It is a 0.3.1 workaround for
  `vec_nodes_active` write-path noise on fresh databases. Carrying a hand-created
  table into an engine that owns its own indexes would be a fabricated schema.
- **`use_default_embedder` stays `False`.** The default is already `False`, and a
  plain `Engine.open` performs **no network access at all**. Turning it on would
  download embedder weights on first use — a network call on a proxy startup path,
  which this deployment does not want. Vector writes then raise
  `EmbedderNotConfiguredError` rather than silently doing nothing; that is the
  correct failure and B-1 must handle it explicitly.
- Adopt the typed error hierarchy (`fathomdb.errors.EngineError`,
  `DatabaseLockedError`, `WriteValidationError`, `OverloadedError`) instead of the
  current bare `except AttributeError` fallbacks in `api/queries.py`.

### The legacy-file guard (added after API review)

0.8.21 will open, report empty, and then write into a 0.3.1 file. Two
complementary moves, because either alone leaves a hole:

1. **Change the default path.** `get_db_path()` currently returns
   `<state_dir>/airlock.db`. Move 0.8.x to a distinct filename so a build pointed
   at an existing state directory cannot adopt the legacy file by default.
2. **Refuse a legacy file explicitly.** Before `Engine.open`, reject a path whose
   file exists and carries 0.3.1-only tables. `fathom_schema_migrations` is a
   clean marker — 0.8.21 uses `_fathomdb_migrations` and never creates the old
   name. `nodes` / `edges` work equally well (0.8 uses `canonical_nodes` /
   `canonical_edges`).

Fail with a message naming the file and saying the 0.3.1 database is abandoned,
not silently side-stepped. An operator who sees "no data" and an unexplained new
file will assume Airlock lost their history.

**Production safety.** The Fathom logger is **off in production**
(`AIRLOCK_ENABLE_FATHOM_LOGGER` unset), so this pack cannot disturb the live
service's request path. Verify before starting rather than assuming — and do the
work in a worktree with `UV_PROJECT_ENVIRONMENT`, per the section above.

**Done when:** a fresh DB file opens, accepts writes, and closes cleanly on
0.8.21; opening a 0.3.1 file **fails loudly with a named reason**, proven by a
test against a fixture legacy file; no `AttributeError`-based capability sniffing
remains; suite green.

## A-2 — Provenance and projections

**`source_id` is the erasure axis**, so choosing it is choosing what erasure can
target. Per the owner decision it is the **authenticated client ID** — the
key-derived `key:<last8>` that `client_id_from_api_key` already produces, and
that the guardrail chain and paid-service allowlist already use.

- Unauthenticated traffic already has a defined value: `client_id_from_api_key`
  collapses a missing identity to `NO_CLIENT_ID` (`no_client`). Use it. FathomDB
  requires `source_id` on every canonical row, and a row without one is
  unerasable — there must be no path that writes without one.
- **Never use the forgeable `X-Airlock-Client` header** as `source_id`. Erasure
  keyed on a client-controlled value would let one caller erase another's records.
  This is the same rule the paid-service allowlist follows.
- Replace the hand-rolled field lists with `engine.configure_projections`,
  declaring which fields are filterable, searchable, and rankable. The engine owns
  every derived index; Airlock stops maintaining any. Concretely:
  `ProjectionSpec(name, roles=frozenset({...}), fts=..., vector=...)` with roles
  drawn from `ProjectionRole.{FILTERABLE, RANKABLE, SEARCHABLE}`, passed as a list
  to `configure_projections(specs, drop=None) -> ProjectionDelta`.
- **Re-configuring projections can be destructive** — `ProjectionDestructiveError`
  exists for exactly that. Treat a projection change as a schema change: inspect
  the returned `ProjectionDelta`, and never pass `drop` casually.
- The mandatory-`source_id` invariant is enforced by the engine
  (`WriteValidationError` / `SchemaValidationError`), so the A-2 test should assert
  the engine rejects a row without one rather than only asserting Airlock supplies
  it. Pin the guarantee, not just our side of it.

**`dev/plan-fathom-storage-implementation.md` is superseded, not executed.** It
specifies a hand-built `fathom:` config surface with `event_fields` /
`payload_fields` and manual index maintenance — all of which 0.8 does natively.
Mark it superseded with a banner pointing here; do not delete it (it is the
contemporaneous design record).

**Done when:** every written row carries a `source_id`; a test asserts no write
path can produce a row without one; projections are declared rather than
hand-maintained.

## A-3 — Port the readers; bound the last unbounded read

`airlock/api/queries.py` is the read surface. All three functions need porting to
`fathomdb.read` (`read.get`, `read.list`, `read.collection`) with an explicit
`ReadView`.

While in the file, fix a leftover: **`get_request_logs(engine, limit=1000000)`**
(`api/queries.py:16`, called by `get_billing_metrics`) is the last unbounded read
of the kind 0.5.9's finding F-4 closed everywhere else. A limit of one million is
a limit in name only, and it materializes every row before aggregating. Bound it
and report truncation the way the advisor tools now do.

The new API helps here: `read.list` defaults to `limit=100`, and
`read.collection` / `read.mutations` make `limit` a **required** keyword. The
unbounded shape is no longer expressible by accident — this pack gets smaller than
originally sized.

`search_logs` is superseded by B-1 — do not port its `fallback_search` +
Python-side substring fallback.

**Done when:** the three datastore consumers work against 0.8.21; no read is
unbounded; truncation is reported rather than dropped.

## B-1 — Hybrid log search (#11)

Issue #11 asks for a hybrid sparse+dense search backend for log searching. **This
stops being a feature to build and becomes one to adopt**: `engine.search()` fuses
FTS5 lexical retrieval with dense vector retrieval, with optional cross-encoder
reranking and JSON filters.

- Expose it through the existing bounded-reader seam so the TUI Logs screen and
  the advisor reach it the same way they reach JSONL today.
- **Ask before searching, don't infer afterwards.** The API review found this is
  cleaner than the plan first specified. `Engine.dense_disabled()` and
  `dense_disabled_reason()` answer directly whether dense retrieval can run, and
  `search_text_only()` is an explicit lexical method. So:
  - if dense is available → `search()`, and report `soft_fallback` if a branch
    still could not contribute;
  - if `dense_disabled()` → call `search_text_only()` and **label the result
    lexical-only**, carrying `dense_disabled_reason()` through to the caller.

  Calling `search()` and hoping the fallback field is noticed is the weaker
  design. A search that quietly returns lexical-only results while presenting
  itself as hybrid is the same defect class as a classifier returning "clean"
  when it could not answer. **Unavailable is not clean, and lexical-only is not
  hybrid.**
- With `use_default_embedder=False` (A-1), dense retrieval is unavailable by
  default, so the lexical-only path is the *normal* path in this deployment, not
  an edge case. Enabling an embedder is a separate owner decision — it performs
  network access on first use — and is out of scope here.

**Done when:** #11's ask is served by the engine; the lexical-only path is
labelled as such and carries its reason; a test asserts a degraded result is
never presented as hybrid.

## B-2 — Per-client erasure (CLI + admin API)

`erase_source(source_id)` removes every row under a provenance together with its
full-text, vector, and secondary-index shadows, and finishes the erasure at rest.
It is idempotent, so an interrupted obligation can be retried.

**It returns an `EraseReport`, and it can fail partway.** The API review found
both: `erase_source` hands back a receipt rather than `None`, and
`fathomdb.errors.ErasureIncompleteError` exists. Two consequences:

- The `admin_action` audit record must carry the `EraseReport`, not a bare "ok".
  An erasure audit trail that records only that the call was made cannot answer
  what was actually removed.
- **A partial erasure must never be reported as complete.** Catch
  `ErasureIncompleteError`, surface it as a failure, and say the obligation is
  outstanding. Retrying is safe — that is what idempotence buys — so the honest
  response is "incomplete, retry", not a success the operator will not revisit.

The capability is useless without a way to invoke it. Two surfaces, both behind
the existing perimeter:

- **Admin API** — `POST /airlock/admin/clients/{client_id}/erase`, added to the
  route table in `admin/http.py:77`. Scope `admin:erase_client`, and
  **`loopback_only=True`** — matching `admin:force_quarantine`, the existing
  destructive operation. It returns an `admin_action` record, so it is audited and
  replicated like every other mutating op.
- **CLI** — `airlock admin erase-client <client-id>`, alongside `mint-token` under
  the existing `admin` subcommand. Requires an explicit confirmation flag; erasure
  is irreversible and must not be a single mistyped word away.

### The scoping constraint that must reach the docs

**FathomDB erasure is not full erasure.** The same records exist in JSONL, which
`erase_source` does not touch. Describing this as "delete a client's data" would
be precisely the over-promise finding F-2 corrected: a claim the code does not
support.

The honest framing, which the documentation must use: this erases a client from
the **search and analysis store**. JSONL retention is governed separately by
`AIRLOCK_MAX_LOG_DAYS`. A user-facing deletion obligation requires both, and the
JSONL half — append-only files under rotation — is **explicitly out of scope for
0.5.11**.

**Done when:** an operator can erase a client from FathomDB via CLI and admin API;
the action is audited; repeating it is safe; the docs state plainly what is and is
not erased.

## F-3 — standing observation, not a deliverable

Per owner decision, code-inspection enforcement stays observational through the
0.5.x line. No default changes in 0.5.11.

Two facts for whoever eventually evaluates it:

- **The window is already running.** `inspect_code` runs on every response
  regardless of weight, so evidence accumulates in the JSONL for free. As of
  0.5.10 closeout: **60 code-bearing responses, zero findings, every score 0.0.**
  The detector was verified working against representative code offline, so that
  is a genuine null result rather than a broken detector — but 60 single-block
  samples is thin, and it points *against* the feared false-positive rate rather
  than for it.
- **A single composite score cannot express the policy.** `restricted_tool`
  (`eval`, `pickle.loads`) is sharp; `resource_access` (`open(`, `requests.`) is
  noisy. They are summed with equal weight into one number, so any threshold
  catching the first also catches the second. If it ever earns a non-zero weight,
  **per-category weights** are the likely shape — not a better single number.

Each closeout appends the current counts. Nothing else.

**0.5.11 closeout (2026-08-07):** 89 code-bearing responses, zero findings,
every score 0.0 (was 60/0/0.0 at the 0.5.10 closeout). The null result
continues to accumulate against the feared false-positive rate.

## Standing constraints

Unchanged from 0.5.10, plus one new:

- Never probe a model from a health endpoint. A test enforces this.
- "Unavailable is never clean" — and in 0.5.11 its analogue: **a degraded search
  branch is never presented as a complete result.**
- `status` is the verdict; `action` is what Airlock did. Keep them separate.
- TUI stays off the request hot path; read through the bounded reader.
- Probe payloads carry no model or provider names.
- **Never write a canonical row without a `source_id`** — an unerasable row is an
  erasure obligation that cannot be met.
- `config.local.yaml` and `dev/competitor-tracker.md` are owner-owned local
  artifacts — never commit them.
